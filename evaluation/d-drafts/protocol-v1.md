------------------------------------------------------------
二、研究問題與立場 [手冊]

RQ1：能選工具補查的 Agent，是否比固定流程提高關鍵主張的證據支持率？
RQ2：加入獨立 Reviewer，是否更能發現並修正預先植入的矛盾、口徑錯誤與不足證據？
RQ3：在相同模型、資料與預算上限下，品質改善是否值得增加的請求、token 與等待時間？

立場：這是小型工程與方法驗證，不預設雙 Agent 一定勝出。負結果、限額失敗、無法改善都要保留。
測試案例數不等於有效獨立財務樣本數。

------------------------------------------------------------
三、三種模式 [手冊]

workflow：程式固定取同一來源快照的前五筆，加上固定的財務、總經與 DCF 輸入快照，模型只寫一次稿。沒有動態選工具，沒有覆核。這是受控基線，不能說和原站所有功能完全等價。
single：Researcher 可以自己選工具、自己決定停止，沒有 Reviewer。
dual：Researcher 加 Reviewer，以及有限次數的補查閉環。

三種模式必須相同的條件：模型 ID 與版本、來源池、cutoff、生成參數。
共用的每個 job 上限：8 次模型發送（含重試）、10 次工具、2 輪補查、180 秒主動時間、准入 40k token。Workflow 不需要硬湊同樣的請求數。
報告時先看相同上限下的比較，再另列每次呼叫的品質（quality-per-call），不能把呼叫較多的優勢說成免費的改善。

四、30 個案例與分組 [手冊]

分組：每類兩個為開發校準（共 10），其餘每類四個為保留測試（共 20）。
開發 10 案：CASE-01、04、08、11、15、18、19、22、26、29。
保留 20 案：其餘（CASE-02、03、05、06、07、09、10、12、13、14、16、17、20、21、23、24、25、27、28、30）。

隔離規則（最重要）[手冊]
1. W06 校準只使用開發 10 案。
2. 保留 20 案只在 W10/W11 的正式評估使用。
3. 不可以拿保留案的答案或輸出去調 prompt、工具或規則。
4. 如果修 bug 後必須重跑，要發新的實驗版本，並保留全部舊結果。
5. D 在 W06 階段不打開保留案的內容與輸出。（本檔作者在確認檔案存在時，只看到封存檔的檔頭與 CASE-02 的標題欄位，已據實記錄，之後不再讀取。）

每個案例固定的欄位：question、cutoff、source_ids、fixture_id、預期可支持主張、預期需拒絕主張、允許的停止狀態、資料來源與授權註記。[手冊]
synthetic_fixture=true 的案例是故意做的錯誤版本，不能說成真實公司真的發生過。[手冊]

五、開發校準怎麼跑（W06 的實驗步驟）

規模：10 案 x 3 模式 = 30 次 run。上限 30 x 8 = 240 次模型請求，實際通常較低。[手冊]
步驟：
1. 確認凍結前的版本：記下 repo commit、prompt 版本與 hash、工具版本、模型 ID。 [D初稿]
2. 每個 run 輸出一列記錄到 dev-runs.jsonl（欄位見 dev-runs-schema.md）。
3. 不管成功或失敗都要寫入，429、timeout、failed 也一樣。[手冊]
4. 評分前，把輸出匿名化並打亂模式標籤，再交給 B 和 D 評分。[手冊]
5. B 和 D 各自獨立評分，先不看對方的分數；有差異由組長裁決，兩份原始分數都保留。[手冊]
6. 校準期間允許用開發 10 案的結果調整 prompt 與工具；調整要記錄每次改了什麼、為什麼。凍結之後就鎖定。[手冊]
7. 全部做完，B 簽 v1、組長核准，才算凍結。凍結時計算每個檔案的 hash，寫進 v12-freeze-report.md。[D初稿，hash 做法需確認]

真實 Gemini 執行的前提（需要別人提供，D 不能自己假設）：
1. 誰來跑、在誰的環境跑。 [待組長確認]
2. API 配額是否足夠，包含 429 的處理。 [待組長確認]
3. 工具資料（財務快照、同業快照、dev 案例證據）以 repo 目前的版本為準，要記下 commit。

mock 與 live 要分開記錄：用模擬（mock）或回放（replay）跑出來的，欄位 run_mode 要寫 mock 或 replay，不能當成 live。[手冊]

六、七項指標（定義來自手冊，分子分母要逐項報告）

1. 證據支持率 = supported 的關鍵可驗證主張數 / 全部關鍵可驗證主張數。沒有主張時回報 NA。另外單獨報拒答率，不能用全部拒答換 100%。
2. 引用可解析率 = 能定位到正確快照且可讀的引用數 / 全部引用數。和「引用有沒有支持主張」分開。
3. 植入錯誤檢出率 = 被指出的植入 critical 錯誤數 / 植入的 critical 錯誤總數。無植入錯誤的案例另報誤報率。
4. 修正率 = 有修正機會的案例中，修正後不再出現同一 critical 錯誤的數量 / 需要修正的數量。只改寫措辭不算修正。
5. 合理拒答率 = 資料不足的案例中，系統選 insufficient 並說明缺口的比例。資料完整卻拒答的另外列出。
6. 作業成功率 = 產出有效格式與正確狀態的 job 比例。429、timeout、failed 都留在總表。可另外報排除刻意故障案例後的比例，但不能只報好看的子集。
7. 成本與效能：每個 job 的模型發送數、usage token、工具數、主動時間、排隊時間、端到端時間、RSS。報中央值、p95、總量，每列附實際 N。沒有帳單時不能填 0 美元，要寫「免費層，本次未計費；已消耗配額」。

每個指標都要同時列：分子、分母、NA 數、樣本 ID、版本。

小樣本提醒：開發 10 案每個模式只有 10 個 run，百分比很容易大幅跳動。報告時必須同時附分子與分母（例如 4/6），不能只寫百分比。[D初稿]

七、不可以做的事 [手冊]

1. 只看文字流暢度打分。
2. 把 mock 當 live。
3. 用保留案的答案調 prompt。
4. 刪掉失敗的 run。
5. 缺值補數字，或把缺值當成 0。
6. 預設雙 Agent 一定比較好。
7. C 和 E 判斷模型準確率或標準答案（他們只整理表格與文書）。
